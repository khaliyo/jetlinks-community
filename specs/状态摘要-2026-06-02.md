## 3. 今日关键认知（排障沉淀）

### 3.1 功能「处理中」与 `REQUEST_HANDLING`

| 现象 | 原因 |
|------|------|
| 界面长期「消息已发往设备,处理中...」 | 物模型 `async:true` + 网关先发 `REQUEST_HANDLING`；broker **首条回复即关闭等待** |
| 执行结果出现 `{ code: REQUEST_HANDLING, message: error.code.request_handling }` | 中间态 JSON；`message` 为 i18n 键名非中文文案 |
| `Mono.empty()` 跳过处理中 | 导致中间态空、最终结果也收不到（已撤销该思路） |

**现行修复（仓库内）：**

- 透传下行 `Headers.async=false`（Connector）
- `invokeFunction`：`.header(async,false)` + 过滤 `REQUEST_HANDLING` + `takeLast(1)`
- [metadata.json](./gspm1b/metadata.json) 功能全部 **`async: false`**

### 3.2 MQTT 两条消息 ≠ 设备回两次

订阅同一 Topic 时 MQTTX 可见：

1. **第一条** — 平台 **下发**（如 `type:event` + `key` + `messageId`）
2. **第二条** — 设备 **上行回复**（`source:command` + `commandName:controller-event`）

方案 A（`/up` + `/down`）后：网关只订 `/up`，JetLinks 不会把下行当上行解码。

### 3.3 单 Topic `/direct` 为何曾采用

对齐 JetLinks 官方 `/direct` 透传约定 + 少改网关；**非协议硬性要求**。长期更合理是 **独立协议 JAR + 上下行分 Topic**。
