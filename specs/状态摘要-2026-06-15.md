## 3. 协议 ID：三层勿混

| 层级 | 示例 | 如何产生 | 用于什么 |
|------|------|----------|----------|
| **JAR / SPI 内部** | `gemeopen-mqtt` 或 `geekopen-mqtt` | Provider 常量 `PROTOCOL_ID` | SPI 默认 id、路由分组；**加载后被 DB id 覆盖** |
| **平台 `dev_protocol.id`** | 雪花 ID 或手动指定 | UI 创建协议时不填 id，后端生成；API 可显式传 | 网关/产品绑定、协议管理列表 |
| **Profile `productId`** | `gspm1b`、`gscw1m2p` | Profile JSON 文件名 | 编解码选配置、Topic 段；**不是**消息协议 id |

**要点：**

- 前台「新增协议」无 id 输入框，保存后取 `response.result.id`。
- `SpringProtocolSupportLoader` 用 `RenameProtocolSupport(definition.getId(), ...)` 包装，**运行时生效的是 DB id**。
- 重复 id 导致 500 的场景：DB 协议 id 与内置 Spring 协议（如 `plugin_gateway`）碰撞，或同一 id 被注册两次——**不是** JAR 内写死 `geekopen-mqtt` 本身导致。

## 5. GemeOpen vs GeekOpen：对比结论

### 5.1 设计文档

| 文档 | 路径 | 特点 |
|------|------|------|
| GemeOpen | [gemeopen/protocol-jar-design.md](./gemeopen/protocol-jar-design.md) | 初版架构、迁移与补丁撤销 §8 |
| GeekOpen v2.0 | `jetlinks/jetlinks-community/docs/geekopen-protocol-design.md` | 三款设备差异矩阵、实施计划、风险；架构与前者同构 |

**文档结论：** GeekOpen 设计文档更完整；两者目标一致（Profile 驱动独立 JAR，替代透传 + 全局补丁）。

### 5.2 代码实现

| 维度 | `gemeopen-protocol` | `geekopen-protocol` |
|------|-------------------|---------------------|
| MQTT 路由 | `/{productId}/{deviceId}/up\|down`，符合设计 | 带 `geekopen-mqtt` 前缀 builder，与设计不一致 |
| MQTT Client 无 DeviceOperator | ✅ `FromDeviceMessageContext` 分支 | ❌ 仅 topic split |
| 上行属性映射 | 只遍历 `propertyMapping` | 遍历整个 payload |
| 事件解码 | Java 硬编码 `controller-event`（Profile 已有 events 未用） | Profile `events` 驱动 |
| 外部 Profile 热更新 | ❌ | ✅ `GEEKOPEN_PROFILES_PATH` |
| `floatProperties` | 硬编码 `FLOAT_SOURCES` | Profile 配置化 |
| 读属性下行 | ❌ | ✅ `encodeReadProperty` |
| 单测 | `Gspm1bCodecTest` 对齐透传 | 有 Decoder 测试，覆盖偏少 |
| SPI / 打包 | shade JAR、`JetLinksDeviceMetadataCodec` | 三模块；无 shade |

### 5.3 性能

- **相对透传 JS：** 任一协议 JAR 均显著更优（编译 Java vs JSR223）。
- **GemeOpen vs GeekOpen：** 同量级；GemeOpen 上行映射路径略优（只扫 mapping）；非选型主因，**正确性与集成完整度**优先。

### 5.4 选型结论

**以 `gemeopen-protocol` 为代码基线**，吸收 GeekOpen 的 profiles 子模块、`floatProperties`、Profile 驱动 events、外部 Profile 目录、读属性下行；合并完成后 **删除 `geekopen-protocol/`**。
