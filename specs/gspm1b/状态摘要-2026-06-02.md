## 2. 当前阻塞问题

### 2.1 功能执行一直「处理中」（主问题，根因已确认）

**现象：** 调用 `powerControl`、`queryInfo` 等，设备已执行，界面仍显示「消息已发往设备,处理中...」（对应 `REQUEST_HANDLING`）。

**根因：**

1. 物模型功能均为 `async: true`，须等设备上行 `INVOKE_FUNCTION_REPLY`，且 `messageId` 与平台下发一致。
2. MQTT 抓包证实 **下行 messageId 不一致**：
   - 平台等待：`2061361985806819328`（雪花 ID）
   - 实际下发 / 设备回包：`1780301970361539`（旧脚本 `nowMessageId()` 自造）
3. 旧脚本上行未在 `source=command` 时构造 `INVOKE_FUNCTION_REPLY`。

**已做修复（仓库内）：**

| 层级 | 改动 |
|------|------|
| `transparent-codec.js` | 删除 `nowMessageId()`；新增 `platformMessageId()` / `withPlatformMessageId()`；上行 `buildFunctionReply()` |
| `TransparentMessageCodecEntity` | `createId()`：`deviceId` 为空用 `""` 而非字面量 `"null"` |
| `TransparentDeviceMessageConnector` | 缓存键 `normalizeDeviceId`；修复查找逻辑 |
| `TransparentMessageCodecController` | 保存后热加载；POST 时 normalize |
| `SimpleTransparentMessageCodec` | 修复 `EventMessage cannot be cast to Optional` |

**待操作：**

1. 重新编译并重启 JetLinks（使 `createId` 等 Java 修复生效）。
2. 清理并重写库中脚本（见 §4）。
3. 验证 MQTT 下行 / 上行 `messageId` 一致，界面由「处理中」变为成功。
4. **勿再单独建设备级脚本**（除非单设备特殊需求），避免覆盖产品级 `gspm1b`。

### 2.2 透传脚本 GET 查不到 / 重启仍像旧脚本

**现象：** `POST` 后 `GET /device/transparent-codec/gspm1b` 无数据；重启后行为仍像旧脚本。

**根因：**

1. **主键 id 算法不一致**：旧逻辑 `String.join("|", productId, deviceId)` 在 `deviceId=null` 时拼成 `gspm1b|null`，与库中 `device_id=''` 的记录 id 不匹配。
   - 旧 id：`e91274f751cbd35f08f565b3072d1a74` = md5(`gspm1b|null`)
   - 修复后 id：`29236c5e949bea513f641e4bc36463e0` = md5(`gspm1b|`)
2. **未带 Token** 时 API 返回 401，易被误认为「空数据」。
3. **设备级脚本** 会覆盖产品级，需 `DELETE /device/transparent-codec/gspm1b/{mac}` 清理。

### 2.3 EMQX 睡眠后无法与 JetLinks / 设备互通（2026-06-02 新报）

**现象：** 昨日正常；电脑睡眠唤醒后 EMQX 无法连上；重启 EMQX 无效；MQTT 客户端能连 EMQX，但 **设备与 JetLinks 服务连不上**。

**已知环境：**

| 组件 | 容器 / 进程 | 端口 |
|------|-------------|------|
| EMQX | `yudao-emqx` | 1883、18083 |
| JetLinks | 本地 Java 进程 | HTTP **3848**（非 Docker 8848） |
| PostgreSQL | `jetlinks-ce-postgres` | 5432 |
| Redis | `jetlinks-ce-redis` | 6379 |

**可能原因（待逐项验证）：**

1. **端口冲突 / 监听错位**：JetLinks 网络组件与 EMQX 均占用 1883；睡眠后 JetLinks MQTT 或 EMQX 监听状态异常。
2. **Docker 网络**：睡眠唤醒后容器 IP / 路由变化，EMQX 规则桥接目标 `127.0.0.1` 指向错误。
3. **JetLinks 进程未重启**：仅重启 EMQX，JetLinks MQTT 客户端连接仍指向旧 socket。
4. **EMQX 规则 / 桥接状态**：规则引擎或 MQTT 桥接在 EMQX 重启后未恢复（Dashboard → 规则 / 连接器状态）。

**建议排查顺序：**

```bash
# 1. 谁占用了 1883
lsof -i :1883

# 2. 容器状态
docker ps -a | grep -E 'emqx|jetlinks|redis|postgres'

# 3. EMQX 日志
docker logs yudao-emqx --tail 100

# 4. JetLinks 日志中 mqtt / gateway / connect 关键字

# 5. EMQX Dashboard (18083) → 客户端：设备、JetLinks 网关 clientId 是否在线

# 6. 若 JetLinks MQTT 与 EMQX 同端口冲突：确认 JetLinks「网络组件」端口（如 1884）与 EMQX 1883 桥接配置一致
```

桥接规则详见 [emqx-bridge.md](./emqx-bridge.md)。

**状态：** 排查未完成（诊断命令曾中断），需用户按上序继续或提供 JetLinks / EMQX 日志片段。

## 3. 数据库：`dev_transparent_codec`

用户反馈「没有 `dev_transparent_codec` 表」——**表实际存在**，多为连错库或未用 Docker 查询。

| 项 | 值 |
|----|-----|
| 容器 | `jetlinks-ce-postgres` |
| 库名 | `jetlinks`（**不是** `postgres`） |
| Schema | `public` |
| 表名 | `dev_transparent_codec` |
| 密码 | `JetLinks@postgres` |

**当前记录（2026-06-02 实测）：**

```text
id:         e91274f751cbd35f08f565b3072d1a74
product_id: gspm1b
device_id:  （空）
provider:   jsr223
脚本:       含 nowMessageId，不含 platform-messageId-v2
```

**查询命令：**

```bash
docker exec -it jetlinks-ce-postgres psql -U postgres -d jetlinks -c \
  "SELECT id, product_id, device_id FROM dev_transparent_codec;"
```

**图形客户端：** Host `127.0.0.1`，Port `5432`，Database `jetlinks`，User `postgres`，Schema `public`。
