## 2. 物模型 enum 显示（近期结论）

### 2.1 现象

透传脚本更新并重启后：

| 属性 ID | 中文名 | 界面表现 |
|---------|--------|----------|
| `switchState` | 开关状态 | 正常（开/关） |
| `onState` | 上电默认状态 | 仍显示 `1.0` 等浮点 |
| `keyLock` | 按键锁 | 同上 |
| `wifiLock` | 配网锁 | 同上 |
| `timerEnable` | 定时上报开关 | 同上 |

### 2.2 根因（共识）

1. **脚本侧**：enum 须上报为 Java `String`（`"0"` / `"1"`），与物模型 `elements.value` 一致；脚本中通过 `ENUM_PROPERTIES` + `toEnumValue()` 处理。
2. **更新频率**：`switchState`（设备字段 `key`）随定时上报频繁刷新，新数据已是字符串；其余 enum 上报少，**设备详情「最新值」仍可能是历史写入的 Double `1.0`**。
3. **不宜在读库展示层「悄悄修正」**：若在 `DeviceProperty` / `ThingPropertyDetail` 把 `1.0` 转成枚举文案，会**只美化旧数据**，并**掩盖后续仍错误上报的 enum**，不利于发现脚本或编解码问题。

### 2.3 已采纳方案

| 层级 | 做法 | 说明 |
|------|------|------|
| 透传脚本 | 保留 `toEnumValue()` / `ENUM_PROPERTIES` | 上行映射见 `PROPERTY_FIELDS` 与 enum 表 |
| 上行编解码 | `SimpleTransparentMessageCodec.normalizeReportPropertiesOnly` | 入库前将整型浮点 enum 规范为 `"1"`（新上报路径） |
| 平台展示层 | **不**做 enum 读库兼容 | 已撤销对 `DeviceProperty`、`ThingPropertyDetail` 的 `coerceEnumInputValue` 改动 |
| 刷新旧最新值 | 设备侧重新上报 | 属性读取、`queryInfo`，或修改上电默认/按键锁等触发 setting 上报 |

### 2.4 验证方式

1. 确认脚本已保存到产品 `gspm1b`（API 或数据解析页签）。
2. 对设备发起 **读取属性** 或 **queryInfo**，使 `onState`、`keyLock`、`wifiLock`、`timerEnable` 产生新上报。
3. 刷新设备详情：应显示枚举文案；若仍为 `1.0`，说明**上行仍为 Number**，应查脚本部署与日志，而非依赖平台展示层兜底。

## 3. 透传脚本要点（enum / int）

```text
ENUM_PROPERTIES: switchState, onState, keyLock, wifiLock, timerEnable
INT_PROPERTIES:  signal, timerInterval

toEnumValue()  → Java.lang.String（避免 JSR223 在 Map 中保留为 1.0）
toJavaInt()    → Java.lang.Integer（int 属性避免界面显示 1.0）
下行 toDevicePayload() → key 等为整数
```

物模型定义见 [metadata.json](./metadata.json) 对应属性的 `enum` 类型。

## 5. 运维备忘

- **存储策略**：产品属性建议 `timescaledb-row`。
- **产品 deploy**：改物模型或存储后需 deploy；`device_log_*` 元数据异常时可参考全过程文档中的启动顺序说明。
- **无「数据解析」页签**：社区版可用 `POST /device/transparent-codec/gspm1b`，见 [README.md § 第三步](./README.md)。
- **配置变更**：`application.yml` / `application-default.yml` 为本地环境，不纳入本 spec 资产。

## 6. 功能执行结果一直「处理中」（2026-06-01）

### 6.1 现象

调用 `powerControl`、`queryInfo` 等功能后，设备已执行成功，但界面执行结果长期停留在 **「消息已发往设备,处理中...」**。

### 6.2 根因

1. 物模型功能均为 **`async: true`**，平台下发后立即返回 `REQUEST_HANDLING`（即上述文案），**真正结束**须等设备上行 **`INVOKE_FUNCTION_REPLY`**，且 **`messageId` 与平台下发一致**。
2. 原透传脚本下行使用 `nowMessageId()` 自生成 ID，**未使用** `context.message().getMessageId()`（平台雪花 ID）。
3. 上行只解析为属性/事件，**未**在 `source=command`（或 `info-all` / `info-statistic` 等指令响应）时构造 `INVOKE_FUNCTION_REPLY`。

### 6.3 已采纳方案

| 层级 | 改动 | 说明 |
|------|------|------|
| 脚本 | `platformMessageId(context)` | 下行 JSON 的 `messageId` 必须使用 `context.message()` 的平台 ID，禁止自造 |
| 脚本 | `buildFunctionReply(data)` | 上行 `source=command` 等场景返回 `INVOKE_FUNCTION_REPLY` |
| 部署 | 重新提交脚本 | `POST /device/transparent-codec/gspm1b` 或数据解析页签 |

### 6.4 验证

1. 重新提交 [transparent-codec.js](./transparent-codec.js)（含 `CODEC_SCRIPT_VERSION = "gspm1b-20260601-platform-messageId-v2"`），保存后立即热加载。
2. **确认未使用旧脚本**：`GET /device/transparent-codec/gspm1b/c82b96f821e2` 若有记录，会**覆盖**产品级脚本；应 `DELETE` 该设备级规则或同步更新设备级脚本。
3. 调用 `powerControl`，MQTT 抓包：下行 `messageId` 须为平台雪花 ID（与日志一致），**不能**是 `1780...` 时间戳格式。
4. 设备上行 `messageId` 与下行相同、`source=command` 时，界面应由「处理中」变为成功。
